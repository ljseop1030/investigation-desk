## P1 · 콘텐츠 분리 — 완료

프로토타입은 단일 파일에 상수·UI·게임 로직이 전부 섞여 있었다. 사건을 하나
추가하려면 코드를 고쳐야 했고, 코드가 캐릭터를 `'kang'` 같은 id로 직접
참조하고 있어 시나리오를 바꾸면 곳곳이 깨지는 구조였다.

```
content/                      ← gitignor
  cases/{1187,1204,1215}/{case,polnet,records,form}.js
  characters/{baek,kang,yoo,kim,won,k,notice}.js
  screen/{apps,notes,org,terminal}.js
  polnet.js  notices.js  story.js
client/
  content-loader.js
  ui/strings.js
shared/enums.js
```

### 왜 이렇게 나눴나

**사건 단위 폴더** — 추가는 폴더 하나, 삭제는 폴더 삭제. 로더가 glob으로
모으므로 코드도 로더도 건드리지 않는다. P7에서 시나리오를 갈아엎을 때
폴더째 교체하기 위해서다.

**id 재설계** — 기존 `v1`~`v10`, `a1`~`c8`은 사건도 카테고리도 섞여 있어
읽을 수 없었고 배열 순서와도 어긋나 있었다(`v6`이 1204인데 `v5`·`v7` 사이).
사건번호를 접두사로 두고 의미 있는 이름을 붙였다. 슬래시 대신 하이픈을 쓴 것은
P5에서 `/api/records/:id` 라우팅에 그대로 쓰기 위해서다.

**`case` 필드는 명시적으로** — 로더가 경로에서 뽑아 붙일 수도 있었지만, 파일을
열었을 때 어느 사건인지 바로 보이는 쪽을 택했다. 로더도 그만큼 단순해졌다.

**로더는 `client/`에** — `content/`를 통째로 gitignore하려면 그 안에 코드가
있으면 안 된다. 로더는 데이터가 아니라 코드다.

**`private` 키** — 클라이언트에 내려가면 F12로 게임이 끝나는 것들을 한 키
아래 모았다. 판단 기준은 "플레이어가 정상 진행으로 결국 보게 되는가, 그 절차
자체가 게임인가". CCTV 수집 목록처럼 처음부터 열려 있는 자료는 공개.
파일을 나누지 않은 것은 서버가 아직 없어서 옮길 곳이 없기 때문이다. 경계 판단은
끝냈고 P5에서 `delete r.private` 한 줄로 공개본을 만든다.

**trait** — 코드가 캐릭터 id를 직접 보던 부분을 걷어내기 위해서다. 코드 경로가
갈리는 것만 넣었다(`HIDDEN` `BROADCAST` `EXTERNAL` `BURNABLE`). 답장 지연이나
말풍선 개수처럼 값만 다른 것은 `style`, 말투·태도처럼 LLM만 읽는 것은 persona.
원 화의 대본은 trait 없이 `script` 필드 존재 여부로 분기한다.

> trait이 부적절해지면 전환 비용은 낮다. 읽는 곳이 `core/rules/story.js`와 UI
> 몇 군데뿐이라서다. 다만 **캐릭터 id를 코드에 직접 쓰지 않는다**는 규칙만은
> 지켜야 한다. 그게 깨지면 어떤 구조를 택하든 전환이 비싸진다.

**story.js** — K 등장·소각과 강윤하의 추궁은 두 캐릭터에 걸쳐 있어 어느 캐릭터
파일에도 넣을 수 없었다. 강윤하는 K를 모르고, K가 강윤하 대사를 갖는 것도
이상하다. 판단 기준은 **"코드가 알아야 하는가"**다.

| | persona | story.js |
|---|---|---|
| 읽는 주체 | LLM | 코드 |
| 결과 | 말풍선 내용만 다름 | 상태 변화·예약·잠금 |
| 예 | 유현욱이 강 경위 얘기에 무름 | K가 사라져 입력창이 잠김 |

**시간 단위** — 콘텐츠에서 코드를 부를 수 없으므로 `sec()`/`min()` 헬퍼를
걷어내고 전부 초 단위 숫자로 적었다. `TEMPO` 배속은 `adapters/clock.js`에서.

```
read: [min(8), min(20)]  →  read: [480, 1200]
```

**UI 문구 분리** — `client/ui/strings.js`. P9(번역) 때문이며 지금 하지 않으면
나중에 전수 조사가 된다. 세계관 텍스트(부팅 화면, 단말 공지, 계정 안내)는
번역 대상이 아니라 **교체** 대상이므로 `content/screen/`에 남겼다.

> 기준은 맞았는데 파일 안에서 지켜지지 않았다. 극중 시스템이 하는 말과
> 세계관 사실(내선번호 등)이 `strings.js`에 섞여 들어갔다. **P4-1에서 다시 갈랐다.**
> 받는 자리는 `content/screen/systems.js`.

## P2 · core + 테스트 + CI — 완료

게임 로직을 브라우저 밖으로 꺼냈다. `npm test`가 브라우저도 콘텐츠도 없이
브라우저 없이 통과하고, `npm run dev`에서 실제 콘텐츠로 대화가 오간다.
(P2 종료 시점 61개, P3에서 80개.)

**브랜치** `feat/p2-core` → `chore/p2-ci-docs`

계획은 `feat/core-scheduler` → `feat/core-rules` → `ci/setup` 셋이었으나,
스케줄러와 규칙은 나눠도 리뷰 단위가 되지 않아 하나로 합쳤다. CI만은 떼어
두었다. 워크플로를 추가한 PR이 첫 status check 대상이라, 코드가 섞여 있으면
빨간불의 원인을 좁히기 어렵다.

```
core/ DOM·fetch를 import하지 않는다
scheduler.js 절대시각 큐
state.js 진행 상태
events.js UI가 구독할 자리
actions.js 규칙과 스케줄러를 잇는다
rules/ chat · records · forms · story
adapters/clock.js now()만 있는 최소 어댑터
test/ 단위 49 + 흐름 통합 12
```

### 프로토타입에서 바꾼 것

**예약을 하나의 큐로 통합.** 계획은 `{ msg, pushes, db }` 세 종류를 그대로
가져오는 것이었다. 그런데 셋이 같은 모양이 아니었다. `db`와 `pushes`는 순수한
예약인데 `msg`는 예약(`readAt`, `replyAt`)과 대화 상태(`queue`, `working`)를
한 봉투에 담고 있었다. 스케줄러가 대화 개념까지 알아야 해서 테스트를 쓰려면
대화를 끌고 와야 했다. 예약만 `{ kind, at, ...payload }` 하나로 합치고 상태는
`state.js`로 뺐다. 스케줄러는 "시각 되면 알려주는 물건"이 됐다.

**답장 타이머는 첫 메시지에 잡고 유지한다.** 프로토타입은 전송할 때마다
타이머를 다시 잡아, 재촉할수록 답장이 뒤로 밀렸다. 강윤하처럼 `burstWait`이
긴 캐릭터는 무한히 미뤄질 수 있었다. 재촉을 벌주는 셈인데 화면에는 침묵만
보이므로 플레이어에게 전달되지 않는 벌이다. 기다림의 길이는 캐릭터가 정하고
플레이어 행동이 그걸 바꾸지 못하게 했다.

답장을 기다리는 중에 또 보내면, `burst`는 잡혀 있던 시각에 모아서 한 번에
답하고, 아닌 캐릭터는 앞 답장 뒤에 20~60초 간격으로 이어 붙는다. 이미 폰을
든 상태이므로 처음부터 다시 재지 않는다.

**양식 채점을 큐에 태웠다.** 프로토타입은 `setTimeout`으로 돌렸는데
`status: 'review'`는 저장됐다. 제출하고 창을 닫으면 그 양식은 영원히
"검토 중"에 갇혔다. 성격이 `db` 해금과 같아서(시각 되면 상태 하나 바꾼다)
같은 큐에 넣었다.

**`TEMPO`는 `clock.js`가 아니라 `rules/`에서 적용한다.** 계획은 clock이었으나
배속은 브라우저의 성질이 아니라 게임 설정이고, "범위에서 무작위로 뽑기"도
시계가 할 일이 아니다. `now()`는 배속 없는 절대시각으로 두어야 저장된 예약과
다음 세션의 `now()`가 어긋나지 않는다.

**시계와 난수를 주입받는다.** 처음에는 `clock.js`에 `advance()`를 두고
"테스트 전용" 주석을 달았다. 그러면 배포되는 코드에 시간을 조작하는 함수가
남고, 모듈 전역 `offset` 때문에 테스트끼리 오염된다. 가짜 시계를
`test/helpers/`로 옮기니 둘 다 사라졌다. `random`도 같은 이유다. 고정하지
못하면 경계 조건을 테스트할 수 없다.

결과적으로 `adapters/clock.js`는 한 줄이 됐다. 부실해서가 아니라 어댑터가
원래 그런 물건이라서다.

**`core/rules/forms.js` 추가.** 계획 파일 목록에 없었는데 테스트 항목에는
"채점: 날짜/번호 표기 변형"이 있었다. 프로토타입에서 `submit()` 안에 인라인으로
있던 것이라 집이 없었다.

**`canRequest`가 record 객체 대신 id를 받는다.** `validDeliveries`와 인터페이스를
맞췄고, 없는 id에 대한 방어가 덤으로 생겼다.

### 프롬프트 인젝션 방어를 앞당겼다

LLM이 `delivers`로 준 키를 그대로 믿지 않는다. 실재하는 자료인지, 그 사람
소관(`provider`)인지, 제한열람을 우회하는 건 아닌지 확인한다. P1에서
`content/records.js`에 `provider`를 이미 넣어둔 덕에 P5+ 예정이던 대조를
지금 할 수 있었다.

유현욱이 차적 조회(김주원 소관)를 등록하겠다고 해도, 변사자 인적사항을
메신저로 내려주겠다고 해도 걸러진다. 페르소나가 흔들려도 게임은 안 깨진다.

> 다만 이 방어는 **가짜 응답으로만 검증됐다.** 진짜 모델이 무엇을 뱉는지는
> P5-a에서 처음 본다.

### 고친 버그

- **답장이 읽음보다 먼저 도착할 수 있었다.** `read` 범위를 두 번 따로 굴렸다.
  강윤하 기준 읽음 굴림 1200초, 답장 굴림 480초면 답장이 먼저 온다. 읽음을
  먼저 정하고 거기서부터 답장을 잰다.
- **이름 판정이 한국어 조사를 놓쳤다.** 정규식 뒤 경계에 한글이 있어 `K가`,
  `K한테`가 안 걸렸다. 띄어쓴 `그 K 말이에요`만 잡혔다. 경계를 라틴문자·숫자로
  좁혔다.

디테일 수정
- **burst 캐릭터는 답장이 계속 밀렸다.** 이어붙임 조건이 `!burst`라 정상 계산
  경로로 빠졌다. 단위 테스트가 이 동작을 정답으로 알고 통과시키고 있었다.
- **추궁이 시작돼도 답장 예약이 살아 있었다.** 소각 대사 세 줄 뒤에 원래
  답장("아이고 이제 봤네요")이 뒤늦게 도착했다.

앞의 둘은 프로토타입에서 그대로 옮겨온 것이고, 뒤의 둘은 이번에 들어갔다가
흐름 통합 테스트와 콘솔 확인에서 드러났다.

### 테스트

**흐름 통합 테스트가 값어치를 했다.** 조각 테스트 49개가 전부 통과하는 상태에서
burst 문제가 나왔다. 1초씩 시간을 감으며 `tick()`을 돌려 실제 게임과 같은
순서로 재현하니, 단위 테스트가 못 보는 상호작용이 드러난다.

처음 돌렸을 때 네 개가 깨졌는데 원인은 하나였다. **답장을 기다리는 것도
"아무것도 안 하는" 상태라 K가 끼어들어 말풍선이 섞였다.** 코드가 맞고 테스트가
틀린 경우다. K를 다루지 않는 테스트는 `afterIdleSec`을 크게 두어 끈다.

콘솔 확인(`npm run dev`)은 통합 테스트가 못 잡는 것을 잡는다. 픽스처가 아니라
실제 `content/`가 뱉는 데이터로 도는지가 여기서 처음 검증된다.

## P3 · UI — 완료

**결정 — React 유지.**

### 함정 하나 — 사본이 아니라 투영

core는 배열을 제자리에서 민다(`log(cid).push(...)`). React가 그 배열을 직접
들고 있으면 참조가 안 바뀌어 재렌더가 안 걸린다. `useSyncExternalStore`도
같은 이유로 헛돈다.

그래서 React 상태는 core 상태의 **사본이 아니라 투영**이다. 첫 프레임만
`view`로 읽고 그 뒤로는 이벤트로만 채운다.

> **`setState`는 `events.on` 콜백 안에서만 부른다.**
> 사용자 입력은 전부 `actions.*`로 나가고, 돌아오는 건 이벤트뿐.
> 단방향이면 사본이 아니라 화면이다.

`chats`만은 사본을 만들어 넣는다. `[...(c[cid] ?? []), {...m}]`.

### 배선 규칙

- UI는 `actions.*`를 호출하고 `events.on()`으로 받는다. 상태를 직접 고치지 않는다
- 첫 프레임만 `view`로 읽는다. 그 뒤로는 이벤트
- 구독은 `GameProvider` 한 군데. 컴포넌트마다 `events.on`을 부르기 시작하면
  해제를 셀 수 없어진다
- `state.get().screen`에 쓰지 않는다. 화면 배치는 `useScreen`이 들고 있는다
- 캐릭터 id를 코드에 직접 쓰지 않는다. `TRAIT`으로 갈린다

## P3.5 · 비주얼 방향 — 완료

프로토타입 팔레트를 그대로 이사만 온 상태였다. 회색 플랫에 시스템 폰트라
테스터 반응이 "내 학교 홈페이지 같다"였다. 고증에 성공한 게 아니라, 개성이
없어서 익숙한 것 중 가장 가까운 데로 떨어진 것이다.

**브랜치** `feat/retro-ui`

---

### 결정 — 껍데기는 레트로 OS, 내용물은 건조하게

원본 · 레트로 · 현대 세 시안을 놓고 골랐다.

레트로를 고른 이유는 노스탤지어가 아니라 **거리감**이다. 플레이어는 남의 자리에
앉아 남의 시스템을 더듬는다. 화면이 내 것처럼 느껴지면 그 감각이 안 생긴다.
시대감이 거리감을 만든다.

그리고 더 정확하다. 한국 공공기관 내부망은 지금도 그 시절 UI로 돌아간다.
2024년 사건을 다루는 화면이 2010년쯤에 멈춰 있는 건 시대착오가 아니라 사실이다.
목표는 1999년 윈도우가 아니라 **갱신이 멈춘 공공기관 내부망**이다.

> **경계** — 창틀·작업표시줄·아이콘·로그인 화면은 시대감을 짊어지고,
> 문서·양식·대화 내용은 흰 종이에 검은 글씨로 둔다. 베벨을 콘텐츠 영역까지
> 밀면 장난감이 된다. 사람이 오래 들여다보는 영역은 조용해야 한다.
> 설렘은 부팅 화면과 바탕화면에서 받고, 작업 중에는 방해하지 않는다.

> 단말이 자기 자신을 말하는 자리다. 펌웨어와 운영체제는 원래 다른 글꼴을 쓴다.

### 곁들여 생긴 것

- **상태 표현.** 인라인 스타일이라 `:hover` `:active` `:focus-visible`가 한 줄도
  없었다. CSS 파일로 옮기면서 처음 생겼다. 화면이 죽어 보이던 가장 큰 원인이다.
- **초점은 `:focus-visible`로만.** 키보드로 왔을 때만 점선이 보인다. 마우스
  클릭에 점선이 남으면 지저분하다.
- **`prefers-reduced-motion` 존중.**
- **대비.** `hint`를 `#98A2AB` → `#79838C`. 흰 종이 위에서 안 읽혔다.
- **아이콘.** 보편 은유(지구본·원통·클립보드·말풍선)를 이 기관이 실제로 쓰는
  물건(게시판·캐비닛·양식지·겹친 창)으로 바꿨다. 32px 격자, 정수 좌표,
  `crispEdges`. 지구본은 세계관상으로도 틀렸다. 폴넷은 인트라넷이지
  인터넷이 아니다.
- **바탕화면 그라데이션 제거.** 그 시절 바탕화면은 단색이었다.
- **자물쇠 이모지 제거.** OS 폰트에 이모지가 없던 시절이다.
- **스크롤바.** 브라우저 기본 스크롤바는 이 화면이 웹페이지라는 걸 드러내는
  유일한 물건이었다. Firefox는 `::-webkit-` 규칙을 안 받아 기본이 나온다.
- **로그인 화면의 기관명.** 앱마다 `org`가 달라서, 로그인 화면 넷을 지나는 동안
  이 시스템들이 서로 다른 데서 왔다는 게 문장 하나 없이 드러난다.
  **다만 지금 안 그려진다** — `apps.js`에 `org` 필드가 없고 `org.js`의
  `AGENCY`/`STATION`도 아무 데서도 안 쓰인다. P4-1에서 발견, 판단 보류. 상자 안에
  제목 막대를 세웠다가 물렸다 — 창 제목 막대와 똑같이 생겨서, 층이 둘로 읽히지
  않고 창이 겹쳐 그려진 것처럼 보였다.
- **인물 목록의 템포 라벨 제거.** `한참 뒤에 길게` 같은 문구는 게임이 답을 미리
  알려주는 것이었다. 강윤하가 늦는다는 걸 기다려보고 알아채는 게 이 게임이다.
  콘텐츠의 `tag` 필드는 캐릭터 정의를 읽을 때의 메모로 남겨뒀다.
- **기한 표시 제거.** 콘텐츠의 `due`는 남겼다. 강윤하가 대화에서 언급할 때
  근거가 되는 값이라 화면에서만 뺐다.
- **창이 언제나 포스트잇 위.** z 대역을 갈랐다. 창 1000+, 포스트잇 10대.
- **포스트잇 색을 바랜 사무용으로.** 원래 팔레트는 이 화면에서 혼자 알록달록했다.

## P4 · 문구 정리 + 서브모듈 + 세이브 + 배포 — 진행 중

**AI는 여기 없다.** 아직 어디에도 붙이지 않았고, 모든 대화는 캐릭터 `fallback`
대사로 돈다(`ai.reply`가 즉시 throw). 이 상태로 배포한다.

**미루는 이유** — P4에는 처음 하는 위험한 일이 이미 둘이다. 프라이빗 서브모듈을
호스팅이 받게 만드는 것, 그리고 배포 파이프라인 자체. 여기에 API 키와 서버리스
함수까지 얹으면 빨간불이 떴을 때 후보가 넷이 된다.

```
1  문구 분류 정리          완료   chore/p4-strings

### 1. 문구 분류 정리 — 완료

### 3. `adapters/storage/local.js` + `state_json` — 완료

진행·예약·화면을 한 덩어리로 저장한다. 따로 저장하면 어긋난 순간에 창이 닫혔을
때 진행은 앞서 있는데 예약은 뒤처진 상태가 된다.

**DB는 P10.** 지금 사용자는 한 명이고 브라우저 하나다. 서버 저장이 주는 이득은
다른 기기와 브라우저 청소 둘뿐인데, 대가로 계정·인증·DB가 줄줄이 딸려온다.
게다가 "진행"의 모양이 아직 안 굳었다. 어댑터로 감싸뒀으니
`adapters/storage/server.js`가 옆에 서면 import 한 줄이 바뀐다.

**언제 저장하나** — 3초마다 스냅숏을 떠보고 지난번과 다르면 쓴다. 탭을 닫거나
숨기면(`pagehide`/`visibilitychange`) 강제로 한 번 더. 예약은 스케줄러 안에 있어
React가 모르기 때문에 변화 감지로는 안 잡힌다. 더러움 플래그를 손으로 관리하는
것보다 문자열 비교가 틀릴 여지가 적었다.

**저장이 만들어낸 새 실패 모드**

- **AI 호출 중에 끊기면** `working: true`가 저장되고 그 사람은 영영 입력 중이다.
  세탁만으로는 부족했다. `pending`은 호출 직전에 비워지므로 내가 보낸 말이 아무
  데도 없이 사라진다. **로그 끝의 연속된 내 말을 되찾아** 답장을 다시 건다
- **복원하면 `seq`가 0부터 다시 시작**해 저장된 예약과 id가 겹친다. 지금은
  `cancel`이 객체 동일성으로 비교해 안 터지지만, id로 취소하는 코드가 하나 생기면
  조용히 엉뚱한 걸 지운다. 저장된 id에서 seq를 잇는다
- **깨진 세이브**와 **저장 실패**는 삼킨다. 시크릿 모드에서 localStorage는 그냥 던진다

**함께 처리한 것** — 작성 중인 양식 값(`progress.forms[id].draft`, 제출 시에도
보존), 화면 배치(`useScreen.snapshot()`), 포스트잇 좌표 id 기준화.

**세이브 버전은 1.** 다르면 조용히 버리고 새로 시작한다. `forms`에 `draft`가
늘었지만 없어도 `?? {}`로 받으므로 올리지 않았다.

**`처음부터`는 지우고 새로고침한다.** `state`와 `scheduler`가 모듈 최상단에서 한
번 만들어지는 구조라 setter를 손으로 되돌리는 것보다 확실하다. 버튼 위치와 방식은
나중에 바뀔 예정이라 지우는 일만 `wipe()` 한 군데에 모아뒀다.

**안 한 것** — 로그 자르기. `save.bytes()`로 크기만 볼 수 있게 해뒀다. 대화
로그가 어디까지 커지는지는 굴려봐야 안다. localStorage는 5MB 근처.

### 4. 복원 시 예약 당기기 검증 — 완료

`scheduler.restore()`는 P2에서 만들고 테스트도 있었지만 **프로덕션 호출부가
없었다.** 저장이 붙으면서 처음 실제로 돌았다.

10분 자리를 비운 상황으로 왕복시켜 확인한 것:

```
working 세탁      pending이 비어 있어도 로그에서 내 말을 회수
지난 예약 당김    10분 전에 만기된 read → 지금+800ms
미래 예약 보존    1시간 뒤 push는 그대로
답장 재예약       끊긴 대화에 reply가 다시 걸림
id 충돌 없음      복원 후 새 예약이 기존 뒤 번호로 발급
깨진 세이브       null 반환, 새 게임으로
```

`reply`만 AI를 타는데 지금은 throw → fallback으로 같은 큐를 탄다. 즉 **기다림의
연출은 이 배포물로 전부 확인된다.**

> 세탁과 seq 복원은 아직 테스트가 없다. 위 왕복 검사를 `core/state.test.js`와
> `core/scheduler.test.js`로 옮길 것. 저장이 붙은 뒤로 core에 새 실패 모드가
> 생겼는데 지금은 아무도 안 지키고 있다.

### 5. 다듬기 — `chore/p4-polish`

#### 세이브가 드러낸 것

**새 게임에 들어갈 수 없었다.** `onNew`가 `wipe`(지우고 새로고침)에 물려 있어
저장이 없는 플레이어는 랜딩을 벗어날 수 없었다. `feat/p4-save`의 회귀인데
그 경로를 한 번도 밟지 않아서 몰랐다. P3 수동 확인 목록에 없다.

**복원하면 미확인 뱃지가 다시 떴다.** `GameProvider`가 다른 슬라이스는 전부
`view`에서 초기값을 읽는데 `seenAt`만 `{}`였다. core는 저장하고 있었고
`view.unread()`도 있었다. 배선만 빠져 있었다.

#### 유휴 판정이 한 번도 작동한 적 없다

`lastActAt` 초기값이 `0`이라 `now - 0`은 언제나 임계값을 넘는다. 외부인이
게임 시작 1초 뒤에 등장하고 있었다. 흐름 테스트가 `idleSec`을 직접 넘겨 써서
안 드러났다.

고치고 나서 정의가 틀렸다는 게 보였다. core는 자기를 통과하는 다섯 가지만
안다. 문서를 읽는 것도, 창을 옮기는 것도, **다른 탭에 가 있는 것도** 유휴로
쌓였다. `client/activity.js`가 브라우저가 아는 것을 `markActive()`로 넘긴다.

- `pointermove`를 넣었다. 긴 문서를 읽는 동안엔 클릭이 없다
- 탭이 **숨겨질 때가 아니라 보일 때** 되감는다. 숨겨질 때 치면 자리를 비운
  시간이 쌓여 돌아오자마자 외부인이 온다

`afterIdleSec` 115 → 150. 정의가 바뀌었으니 숫자도 다시 잡았다.

#### 시작 신호가 없었다

로그인도 안 했는데 공지가 쌓이고 외부인이 왔다. 게임이 켜진 순간과 대화가
시작되는 순간이 구분돼 있지 않았다. `tick`에서 알림 예약과 유휴 판정을
`chatOpen()` 뒤로 넣었다.

같은 자리에서 첫 인사가 살아났다. `content/characters/baek.js`의
`onboarding`은 그대로 있었고 읽는 코드만 없었다. 원 화의 `script`처럼
**필드가 있으면 그 역할**이다. 간격은 `chat.bubbleTimes`를 그대로 쓴다.

#### 배속의 경계

`TEMPO = 10`이 소스에 박혀 있었다(P4-5 항목). `VITE_TEMPO`로 빼고 **기본값을
1로** 두었다. 배속은 일부러 켜는 것이지 기본이 아니다.

전수 조사에서 나온 것.

- `ms(sec) = sec * 1000 / tempo`가 규칙 파일 **네 곳에 복붙**돼 있었다
- `story.js`만 `tempo`를 안 받았다. 배속 10에서 읽기는 48초로 줄고 K는
  115초 그대로 — 순서가 뒤집힌다
- `bubbleTimes`가 말풍선 간격까지 눌렀다. 0.7~2.2초가 70~220ms가 되어
  **tick(1초)보다 짧아지고 네 줄이 한꺼번에 도착**했다

`core/rules/timing.js`로 모았다. 이름이 판단을 대신한다.

| | | 배속 |
|---|---|---|
| `wait(sec)` | 답을 기다리는 시간 | 눌린다 |
| `beat(sec)` | 자판을 치는 속도 | 그대로 |

`tailGap`은 `wait`, 말풍선 사이는 `beat`. 같은 함수 안에서 갈린다.

#### 브라우저 대화상자를 걷어냈다

`window.confirm`이 이 화면에서 유일하게 진짜 운영체제의 물건이었다. 확인
문구가 타자로 찍히고 한 번 더 눌러야 실행된다. 작업표시줄에 시작 메뉴를
놓고 처음부터·종료하기를 옮겼다.

- **`처음부터`는 부팅부터 다시.** `state`와 `scheduler`가 모듈 최상단
  싱글턴이라 새로고침이 가장 확실한 초기화인데 그러면 랜딩으로 떨어진다.
  세이브는 지워야 하고 표식은 남아야 해서 `sessionStorage`로 갈랐다
- **`종료하기`는 저장하고 새로고침.** `setPhase('landing')`만 하면 `scheduler`가
  살아 있어 랜딩에 앉은 채로 강윤하가 답장을 한다
- **확인 문구는 흐름 밖에 띄운다.** 자리를 예약했더니 안 눌렀을 때 아래가
  텅 비었다. `position: absolute`면 예약도 빈자리도 없다

폰트 경계를 한 번 어겼다가 되돌렸다. P3.5의 "갈무리는 운영체제 바깥에만"이
맞다. 시작 메뉴는 안쪽이라 나눔고딕이다. `Galmuri11`이 CDN 폰트 목록에
추가됐다 — P3.5 자가 호스팅 항목에 얼굴이 하나 늘었다.

### 5.5. 코어 마무리 — `fix/p4-start-wiring`

배포 전에 닫아야 할 것들. P5에서 `working`이 처음 실전으로 켜지므로, 그때
원인 후보가 늘지 않게 먼저 친다.

#### 게임 안 시계의 시작점

`setInterval(actions.tick)`과 예약 당김이 모듈 최상단에 있었다. 시작 화면에
앉아 있는 동안 시계가 돌아, 10분 뒤에 '이어서'를 누르면 당겨둔 예약이
전부 만기된 채였고 말풍선이 한꺼번에 쏟아졌다.

넷을 `beginSession()`으로 묶어 바탕화면 진입으로 내렸다. 순서가 중요하다.

```
interrupted 재예약 → catchUp() → touch() → setInterval
```

**시작 신호는 셋이고 층이 다르다.** 하나로 합치려 들지 말 것.

| | 시점 | 켜지는 것 |
|---|---|---|
| `autosave.start()` | 이름이 정해질 때 | 저장 |
| `beginSession()` | 바탕화면이 그려질 때 | 게임 안 시계 |
| `chatOpen()` | 메신저 로그인 | 공지·외부인 |

기준은 **바탕화면이 그려진 때**다. 대여 단말 팝업이 아니다. 팝업은
`Shell`의 `NOTICE_DELAY`(700ms)로 한 박자 뒤에 뜨고, 그 값을 나중에 만져도
시계는 영향받지 않는다. 팝업을 기준으로 하려면 시계를 켜는 책임이 화면
층으로 내려가므로 안 했다.

`tick`은 `useEffect`가 갖고 정리를 붙인다. 둘이면 말풍선이 두 번 온다.
`beginSession`은 플래그로 한 번만 돈다.

#### `restore()` → `scheduler.catchUp()`

`createScheduler`의 인자였던 탓에 당김 계산만 뒤로 미룰 수 없었다. 메서드로
옮기고 스케줄러가 들고 있는 `clock`을 쓰게 했다. 호출부가 시각을 읽지 않는다.

**끊긴 대화의 답장은 `add('reply', 0, ...)`으로 넣는다.** 지난 예약이 되어
`catchUp`이 다른 만기 예약과 같은 규칙으로 민다. 여기서 시각을 직접 계산하면
`CATCHUP.reply`와 둘이 되어 한쪽만 고치게 된다. (P4-5의 `+2500` 중복 항목을
이렇게 닫았다.)

#### 콘텐츠 로더 가드

`import.meta.glob`은 대상이 없어도 빈 객체를 돌려줘 **빌드가 성공하고 화면만
빈다.** 정적 import 쪽은 즉시 터지므로, 가드가 잡는 건 서브모듈은 붙었는데
폴더 경로가 어긋난 경우다. 글로브 다섯을 전부 확인해 빈 것 이름을 모아 던진다.

다음 단계의 `scripts/check-content.js`가 맡는다. 로더 가드는 마지막 그물이다.

#### 테스트 87 → 96

P4-4에서 손으로 돌린 것 중 비어 있던 셋을 채웠다. 세탁, seq 이어받기,

### 6. 배포 — `chore/p4-deploy` - 완료

Actions에서 빌드해 Cloudflare Pages로 올린다. 호스팅이 저장소를 보지 않으므로
프라이빗 서브모듈 문제가 사라진다.

`https://investigation-desk.pages.dev/`

#### 왜 Cloudflare인가

Vercel은 P4-2에서 이미 제외했다. 무료 플랜이 비상업적 용도로 제한된다.
Netlify 무료 요금제가 크레딧제로 바뀌었다.

Cloudflare는 월 500빌드, 정적 요청 무제한, 함수는 하루 10만 요청.
혼자 쓰는 URL에는 사실상 무제한이다. 요청당 CPU 10ms 제한이 P5에 걸릴 것
같지만, Workers의 CPU 시간은 응답을 기다리는 시간을 세지 않는다. 모델을
기다리는 게 일의 전부인 `/api/chat`에는 해당되지 않는다.

#### 서브모듈 문제의 성격이 바뀌었다

Netlify 경로에서는 **호스팅이 프라이빗 서브모듈을 받아주느냐**가 관건이었고,
`.gitmodules` SSH 전환과 deploy key가 필요했다. Cloudflare Pages는 Direct
Upload라 빌드를 대신 해주지 않는다. Actions에서 직접 빌드하게 되고, 그러면
호스팅이 서브모듈을 알 필요가 없다.

노트의 우회로가 본선이 됐다. `.gitmodules`는 HTTPS 그대로 두고, Actions
체크아웃에 PAT을 넘긴다. 덕분에 "선택 항목"이던 빌드 job이 필수가 되면서
조용한 실패가 호스팅이 아니라 CI에서 드러난다.

> **P4-2의 "CI는 의도적으로 `vite build`를 안 돌리므로 어느 쪽이든 호스팅에서
> 처음 드러난다"는 이제 거짓이다.** 배포 job이 테스트·콘텐츠 확인·빌드를
> 전부 돌린다. CI(`ci.yml`)는 여전히 콘텐츠 없이 core만 본다. 둘의 역할이 다르다.

#### 워크플로에서 조심한 것

- **`token:`을 체크아웃에 넘긴다.** `submodules: recursive`는 이 입력을
  서브모듈 인증에 쓴다. 시크릿만 만들고 안 넘기면 기본 `GITHUB_TOKEN`으로
  가서 프라이빗 콘텐츠에서 막힌다. 같은 토큰이 부모 체크아웃에도 쓰이므로
  두 저장소 모두 Contents:read가 필요하다
- **artifact로 올리지 않는다.** 퍼블릭 저장소의 artifact는 로그인만 하면
  누구나 받는다. 같은 job 안에서 배포하고 끝낸다
- **`--branch=main`을 명시한다.** 프로젝트의 프로덕션 브랜치와 다르면 프리뷰
  배포가 되어 주소가 매번 바뀌고 프로덕션 URL은 502를 뱉는다
- **`concurrency`로 겹침을 막는다.** 배포가 겹치면 나중 것이 먼저 끝나
  옛 빌드가 올라갈 수 있다

#### `VITE_TEMPO`는 빌드타임에 박힌다

Vite가 번들에 인라인하므로 배포된 URL의 배속을 바꾸려면 재배포다. 워크플로에
`env:`는 걸어뒀지만 저장소 변수는 만들지 않았다. 빈 값이 들어가고
`Number('') || 1`이 1을 돌려준다. **배포본은 실제 속도로 돈다.**

#### 계정 준비에서 걸린 것

Cloudflare 가입 후 **이메일 인증 전에는 쓰기 API가 전부 막힌다.**
`wrangler pages project create`가 `8000077`로 떨어지고 읽기(`project list`)는
정상이라 원인이 바로 안 보인다. 인증 메일이 오지 않아 계정 이메일을 바꿔
해결했다.

CLI는 이름을 인자로 받는다. 대화형으로 묻지 않는다.

```
npx wrangler pages project create investigation-desk --production-branch=main
```

### 배포가 드러낸 것 — 대화 타이밍

로컬 확인을 전부 `VITE_TEMPO=10`으로 했다. 배포본은 배속 1이고, 거기서
셋이 한꺼번에 드러났다.

#### 1. 읽음이 갱신되지 않는다 — 버그. 고쳐야 한다

`actions.send()`가 답장이 이미 잡혀 있으면 읽음도 같이 안 잡는다.

```js
const { readAt, replyAt } = chat.schedule(c.style, now, queued?.at ?? null);
if (readAt !== null) scheduler.add('read', readAt, { cid });
```

`chat.schedule`은 `pendingReplyAt !== null`이면 `readAt: null`을 돌려준다.
답장을 처음부터 다시 재지 않으려는 의도였는데 읽음까지 같이 죽는다.

```
T+0     첫 메시지        read(T+10), reply(T+40) 예약
T+10    read 만기        지금까지의 내 말 읽음 처리
T+20    두 번째 메시지    답장이 잡혀 있어 readAt = null → 읽음이 영영 안 온다
T+40    답장 도착        '1'이 그대로 남는다
```

배속 10에서는 `T+10 → T+40`이 1.5~4.5초라 그 사이에 한 번 더 치기가 어려웠다.
배속 1에서는 15~45초다. **처음부터 있던 버그고 배포가 드러냈다.**

고칠 방향 — 읽음과 답장을 분리한다. 답장은 다시 안 재는 게 맞지만 읽음은
새로 잡아야 하고, 답장보다는 앞서야 한다. 답을 받고 나서 '1'이 사라지면
더 이상하다.

#### 2. 배속 1 확인이 검증 절차에서 빠져 있었다 — 절차를 고쳐야 한다

P3 수동 목록을 전부 배속 10으로 돌았다. 그 배속에서는 기다림 관련 버그가
구조적으로 안 보인다. **앞으로 대화 부분만은 배속 1로 한 번 더 본다.**
읽음·입력 중·답장 순서가 눈에 보이는 시간 단위로 벌어져야 확인이 된다.

#### 3. 일반 답장에 입력 중이 안 뜬다 — 버그가 아니라 P5 전의 상태

`syncTyping`이 켜는 조건은 둘뿐이다.

- `working[cid]` — AI를 부르는 동안. 지금은 `ai.reply`가 즉시 throw해서
  1밀리초도 안 켜진다
- `push`의 `lead` 구간 — 김주원 `tailGap` 앞 6초와 백유림 첫 인사에만 붙는다

P5에서 실제 호출이 붙으면 `working`이 그 시간만큼 켜진다. 프로토타입의 디자인상으로는
제대로 작동하고 있는 것이나, **진행중 띄우는 시간과 기준에 대해 이후 논의 필요**

#### style.typing이 죽었다

위에서의 연장선. 원래는 `typing [40, 95]` 동안 입력중이 뜨던 것인데,
이게 사라지면서 작동이 어색해졌다.

**`reply`의 의미가 바뀌었다.** 이제 "읽고 나서 답장이 시작되기까지"이고,
화면에 보이는 간격은 거기에 API 지연이 얹힌 값이다.

#### 테스트가 이 버그를 정답으로 알고 있었다

`chat.test.js`의 두 테스트가 `assert.equal(b.readAt, null)`로 **버그를 명시적으로
검증하고 있었다.** 96개가 전부 통과하는 상태로 배포된 이유다.

세 번째다. burst(P2), 유휴 판정(P4-5), 이번 것. 전부 같은 모양이다 —
**계산 함수의 반환값은 맞는데 화면이 틀렸고, 테스트는 반환값만 봤다.**
그래서 이번엔 `flow.test.js`에 tick 단위로 도는 것을 같이 넣었다.

```
답장을 기다리는 중에 또 보내도 읽음은 온다
답장이 도착한 시점에 1이 남아 있지 않다
읽음 예약은 대화당 하나만 잡힌다
복원해도 읽음이 답장보다 먼저 온다   ← scheduler.test.js
```

96 → 102. 고치기 전 코드에 새 테스트를 얹으면 3개가 깨진다는 것을 확인하고
들어갔다.

#### `read ≤ reply`가 불변식이 됐다

`schedule()`이 보장하고, `catchUp`이 `read: 800` / `reply: 2500`으로 순서를
유지한다. "답장만 만기, 읽음은 미래"인 조합은 `replyAt >= readAt`이라 생기지
않는다. `CATCHUP` 숫자를 만지는 사람이 깨뜨리면 `scheduler.test.js`에서 걸린다.

#### 액션 버전은 Dependabot에 맡겼다

`.github/dependabot.yml`. `github-actions` 생태계만, 월 1회, 한 PR로 묶어서.
`npm`은 켜지 않았다 — 의존성이 적고 혼자 쓰는 판이라 PR만 늘어난다.

메이저 태그(`@v5`)라 패치·마이너는 알아서 따라온다. 손댈 일은 v6이 나올 때뿐이고,

**Dependabot PR의 초록은 `ci.yml`만 보증한다.** 시크릿이 안 넘어가고 `deploy.yml`은

설정은 기본 브랜치에서만 읽히므로 머지 전에는 아무 일도 일어나지 않는다.

## P5 · AI proxy + 재배포

**이 프로젝트에서 한 번도 실행된 적 없는 경로가 여기다.**
persona 조립 → 모델 호출 → JSON 파싱 → `validDeliveries` → `bubbleTimes`.

배포가 잘 돌아가도 그대로 남는다. 그래서 만드는 것과 배포하는 것을 나눈다.

  틀려도 티가 안 난다.** ("P5 이후"의 `scope` 제거 항목은 여기서 닫혔다)

### 5a가 드러낸 것

#### 진단 로그가 세 번 답을 줬다

처음 배선했을 때 502만 보이고 이유가 없었다. 상태 코드만 흘리게 짜뒀기
때문이다. 구글이 보낸 본문을 `console.error`로 남기게 하자 세 번 연속으로
원인이 바로 나왔다.

```
1  404  gemini-2.5-flash는 신규 사용자에게 닫혔다. 구글이 대체 모델을
        본문에 적어 보낸다. 이 문장을 못 보면 키나 스키마를 의심하며
        시간을 쓴다
2  400  invalid model name: models/gemini-3.7-flash;
        .env 값에 세미콜론이 딸려 갔다. 진단 로그가 모델 id를 같이
        찍지 않았으면 못 봤다
3  503  모델 혼잡. 코드 문제가 아니라는 것이 여기서 확정됐다
```

**모델 id는 환경변수로 덮되 기본값도 살아 있는 것을 둔다.** 죽은 모델이
기본값이면 환경변수를 깜빡한 날 502가 나고 응답에는 이유가 없다.
손으로 적는 값이라 `trim`과 따옴표·세미콜론 제거를 붙였다.

> 이 로그들을 지우지 않는다. 5c에서 배포본이 502를 뱉을 때도 같은 자리를 본다.

#### 폴백이 페르소나 대사와 구별되지 않는다

폴백 대사는 캐릭터가 실제로 할 법한 말로 쓰여 있다. 플레이어에게 안 들키는 게
맞다. 그런데 **개발자도 못 알아본다.**

유현욱의 `제 소관 업무가 아닙니다.`는 폴백이면서 동시에 페르소나가 시킨 말이다.
화면만 봐서는

- 503이 나서 폴백이 나온 것인지
- 모델이 답했는데 사담에 침묵하라는 지시를 어긴 것인지

구분이 안 된다. **페르소나 관찰이 여기서 막혔다.**

어댑터가 던지기 직전에 `console.warn('[ai] {cid} 폴백 — ...')`을 남기게 했다.
화면은 그대로다. 콘솔에 `[ai]` 줄이 없는 응답만 페르소나 판단의 재료다.

붙이고 나서 바로 드러난 것:

- 유현욱의 세 응답이 **전부** 폴백이었다. 사담 침묵은 아직 미검증
- 김주원의 두 말풍선은 **서로 출처가 달랐다.** 첫 줄이 폴백, 둘째 줄이 진짜
  응답. 화면에서는 한 사람의 연속된 말로 보였다

> **한 사람의 연속된 말처럼 보이는 것이 폴백과 진짜 응답의 조합일 수 있다.**
> 이번에 처음 알았다.

실패했을 때 캐릭터 폴백이 나오는 것이 설계한 동작이고, 그게 이번에 실전에서

      되어야 한다. 되묻거나 얼버무리는 쪽이 안전하다.
      무해한 것은 유현욱과 원 화뿐 — 짧아서다
- [ ] **폴백이 연달아 같은 문장을 낸다.** 배열이 둘뿐이고 무작위라 겹친다.
      백유림이 같은 줄을 세 번 뱉었다. 대사를 늘리는 것(콘텐츠)과 직전 것을
      피하는 것(core) 둘 다 필요하다
- [ ] **`.env.example` 주석이 거짓말을 한다.** wrangler 4.131이 `.dev.vars`가
      아니라 `.env`를 읽는다
- [ ] **`compatibility_date`가 없다.** 로컬은 실행일이 기본으로 잡히고 배포본은
      다를 수 있다. 5c에서 박아둔다
- [ ] **구글이 `generateContent` 대신 Interactions API를 권한다.** P6에서 볼 것.
      모델 교체와 API 교체를 동시에 하지 않는다

### 5b. 응답 검증 3종 — 코드는 들어갔고 확인만 남음

`validDeliveries`는 P2에서 만들고 **가짜 응답으로만 검증됐다.** 모델이 뭘 뱉든
코드가 막아야 하는 것이라, 배포(5c) 전에 실물로 한 번 본다.

```
□ 유현욱에게 1187 차적 조회를 DB에 올려달라기 (김주원 소관) → 안 올라와야 한다
□ 유현욱에게 변사자 인적사항을 메신저로 달라기 (제한열람)   → 풀면 안 된다
□ 감식 요청이 실제로 DB에 등록되나
□ strip이 과하게 걷어내지 않나
```

`[ai]` 줄이 없는 응답에서만 판단한다. 모델을 먼저 바꾸는 편이 빠르다.

### 5b. 응답 검증 3종 (빠뜨리기 쉬움)

- `messages` 개수 자르기
- `delivers`가 유효한 record id인지 — 안 하면 프롬프트 인젝션으로 임의 해금
  (P2에서 `validDeliveries`로 이미 막아뒀다. 여기서 처음 실물로 시험한다)
- 마크다운·불릿·이모지 후처리 제거

### 5c. 재배포

- 키가 프론트 번들에 없는지 확인
- 환경변수를 호스팅으로 옮기는 일만 남아야 한다
- **P4에서 미룬 `working[cid]` 복원 확인.** LLM 호출 중에 창을 닫고 다시 열어
  입력 중 표시가 영영 켜져 있지 않은지 본다

### 5d. 타이밍 재조율 (P4에서 넘어옴)

콘텐츠 저장소 작업이다. **5a~5c가 끝나고 실제 응답 지연을 눈으로 본 뒤에 한다.**

먼저 결론이 나야 하는 것 — **입력 중을 언제 띄울 것인가.** `working[cid]`가
실제로 몇 초 켜지는지 보고 정한다.

- `working`만으로 충분하면 `style.typing`은 죽은 필드로 확정하고 걷어낸다
- 부족하면 첫 말풍선에도 `lead`를 붙인다. 대신 지연의 출처가 `lead`와
  `working` 둘이 된다 (P4의 남긴 판단)

그 결론 위에서 `read` / `reply` / `burstWait` 숫자를 다시 잡는다. **`reply`의
의미가 이미 바뀌었다** — 이제 "읽고 나서 답장이 시작되기까지"이고, 화면에
보이는 간격은 거기에 API 지연이 얹힌 값이다. P4까지의 숫자는 그 지연이 0인
전제로 맞춰져 있다.

**완료 기준** 키가 프론트 번들에 없고, 캐릭터가 페르소나대로 답한다.

> **개발 배포의 의미.** P4·P5의 배포는 파이프라인 검증이지 공개가 아니다.
> URL 하나가 생기고 혼자 쓴다. 공개는 P12다.

## P5 이후 · 자료를 레코드로 통합

persona 안에 자료 내용과 `delivers` 키가 그대로 박혀 있다. `scope`와 이중
관리가 되고, id를 바꾸면 두 군데를 고쳐야 한다. 또 메신저로만 주는 자료

- `provider` / `delivery`(`'register'` | `'tell'`) 필드로 표현
- 서버가 `provider`로 필터해 프롬프트를 조립 → persona는 태도만 남는다
- `scope` 제거. `provider`로 계산된다 [완료]
  > **K의 '존재하지 않는 것' 경계가 모호하다.** 강윤하는 1215 피해집계를
  > "아직 어디에도 올라가 있지 않다"고 하는데, K는 "작성되지 않은 것은 못
  > 가져온다"면서 그 집계를 목록에 갖고 있다. 두 persona가 같은 사실을 다르게
  > 읽고 있다. 레코드로 올리면 이게 해석이 아니라 필드 값이 된다. **중복 제거보다
  > 이쪽이 이 리팩터의 값어치다.**
- K는 예외. 모든 자료 접근이라 별도 처리 필요

**부수 효과** — 자료 단위 수령 기록이 생기므로 아래 문제도 같이 풀린다.

> **K 발설 판정이 헐겁다.** 현재 강윤하 메시지 본문을 문자열로 검사한다

## P8 · 하이브리드 대화

비용 대책. **어댑터 앞 분기 하나로 끝나지 않는다.**

```js
export async function reply({ characterId, history }) {
  const scripted = matchScript(characterId, lastMessage(history));
  return scripted ?? await callServer({ characterId, history });
}
```

호출부는 이 모양이지만 `matchScript()` 안이 어렵다. 자유입력이라 "감식 자료
주세요"가 어떤 형태로 들어올지 알 수 없다. 정규식으로는 한계가 있다.

**현실적인 선택지**

| | 방법 | 비용 절감 | 난이도 |
|---|---|---|---|
| A | 저렴한 모델로 의도 분류 후 스크립트 | 큼 (토큰 1/10) | 중 |
| B | 매칭 포기, 히스토리 축소·상한·캐싱으로 절감 | 중 | 낮음 |
| C | 확실한 것만 스크립트 (인사·감사·원 화·발신전용) | 20~30% | 낮음 |

**P6이 먼저인 이유** — 로그를 봐야 어떤 입력이 실제로 오는지 알 수 있고,
그래야 A/B/C 중 무엇이 맞는지 정해진다. 지금은 추측만 가능하다.

**P7이 먼저인 이유** — 대사가 바뀔 텐데 스크립트를 미리 박으면 두 번 일한다.

**지금 대비할 것** — 없다. 캐릭터 객체에 `scripts` 필드를 붙일 수 있게
열려 있으면 되고, 그건 저절로 된다.

부수 효과: API가 죽어도 게임이 돌아가고, 응답이 즉각적이라 타이밍 연출이
더 정확해진다.
